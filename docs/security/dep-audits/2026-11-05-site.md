## Scope and decision

## Security findings still open

`bun audit --no-env-file` reports **12 advisories: 1 critical, 3 high, 5 moderate, and 3 low** after the updates. These are registry findings, not confirmed application exploits. This update must not be described as security-clean or production-ready.

| Package/path | Remaining findings | Reachability and required action |
| --- | --- | --- |
| Direct astro@6.4.8, also peered by integrations | 1 critical, 4 moderate, 1 low | Includes AVIF optimization RCE, spread/transition/MDX escaping, and base-path authorization issues. The configured production image service uses Cloudflare Images; build-time image processing uses Sharp. The critical advisory requires processing attacker-controlled AVIF. Deployment exploitability was not tested. Upgrade the framework and integrations together; Astro 7.4.7 is the current registry target. |
| Direct sharp@0.34.5 and astro > sharp | 3 high | libvips/libheif/librsvg advisories. Trust of input images matters; do not assume repository-owned content makes every processing path safe. Sharp 0.35.5 is the registry target. Updating only the direct Sharp package would leave Astro's ^0.34 copy vulnerable. |
| astro > esbuild and Vite 7 > esbuild@0.27.7 | 1 low | Windows development-server file-read issue. The reported path is esbuild's server, not evidence that the Astro server exposes it. Fixed at >=0.28.1; current parent ranges retain 0.27. Wrangler also resolves a separate patched 0.28.2 copy. Coordinate the parent updates with Astro 7/Vite 8 instead of forcing an incompatible override. |
| rehype-mermaid > mermaid-isomorphic > katex@0.16.47 | 1 low | Prototype-pollution-assisted trust bypass. This stack renders repository-authored diagrams during compilation. No exploit was tested. Fix requires KaTeX >=0.18.2 and an upstream-compatible Mermaid rendering stack. |
| @cf-wasm/og > @cf-wasm/satori > satori@0.26.0 | 1 moderate | Improper SVG escaping. The public OG endpoint accepts query values, but returns rasterized PNG rather than SVG. That does not prove the issue is harmless. Fix requires Satori >=0.33.5; evaluate @cf-wasm/og 0.5.0 and its resolved graph separately. |

Primary advisory cross-checks:

- [Astro AVIF advisory GHSA-26w7-cxv4-gfx2](https://github.com/advisories/GHSA-26w7-cxv4-gfx2) fixes the issue in Astro 7.2.8 with Sharp >=0.35.4. Sharp's additional librsvg advisory requires 0.35.5.
- [Satori advisory GHSA-wx4j-mvgx-mqwp](https://github.com/advisories/GHSA-wx4j-mvgx-mqwp) requires 0.33.5 and states that impact depends on how the generated SVG is consumed.

No remaining risk was accepted on the user's behalf. Do not suppress the advisories.

## Next update set

Restore the missing RepoGrid source so production build and type-check verification can complete. Then migrate Astro and its official integrations as a coordinated change, together with Vite 8 and Sharp 0.35.5 or newer.

The [Astro 7 migration guide](https://docs.astro.build/en/guides/upgrade-to/v7/) describes a new default Markdown processor, Vite 8, stricter Rust compilation, and whitespace changes. This project has custom rehype Mermaid processing and a Vite 7 override, so a blind `bun update --latest` is not appropriate. Preserve the actual Mermaid behavior with the supported Markdown processor configuration and remove the obsolete Vite-major pin as part of that migration.

Other deferred registry majors include TypeScript 7, Vitest 5, Cloudflare Workers types 5, unplugin-icons 24, and prettier-plugin-astro 1. Evaluate them separately from the compatible baseline. The OG renderer and KaTeX parent updates need their own resolved-graph/security checks.
