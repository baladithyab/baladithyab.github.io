## Scope and decision

Review the Bun-managed dependency graph, update compatible releases, refresh `bun.lockb`, and exercise the site. This is not a complete license, maintainer, or supply-chain audit. No deployment or commit was performed.

Keep Astro 6, its Cloudflare 13 adapter, Vite 7, TypeScript 6, and Vitest 4 together. Preserve the existing Vite-major override, but raise its minimum to 7.3.7. ## Next update set

Verify the complete committed tree in CI or isolate the local working-copy deletions for further local build checks. Then migrate Astro and its official integrations as a coordinated change, together with Vite 8 and Sharp 0.35.5 or newer.

The [Astro 7 migration guide](https://docs.astro.build/en/guides/upgrade-to/v7/) describes a new default Markdown processor, Vite 8, stricter Rust compilation, and whitespace changes. This project has custom rehype Mermaid processing and a Vite 7 override, so a blind `bun update --latest` is not appropriate. Preserve the actual Mermaid behavior with the supported Markdown processor configuration and remove the obsolete Vite-major pin as part of that migration.

Other deferred registry majors include TypeScript 7, Vitest 5, Cloudflare Workers types 5, unplugin-icons 24, and prettier-plugin-astro 1. Evaluate them separately from the compatible baseline. The OG renderer and KaTeX parent updates need their own resolved-graph/security checks.

## PR #44 follow-up

After the Astro 7 migration, the remaining native-audit findings were Satori
0.32.0 (moderate) and KaTeX 0.16.47 (low). The new graph reports **no known
vulnerabilities across 737 checked packages** with `bun audit --no-env-file`.
This is a registry-advisory check, not a complete security or supply-chain audit.

### OG renderer decision

`@cf-wasm/og@0.5.0` still resolves `@cf-wasm/satori@0.4.2`, which pins Satori
0.32.0. An experimental scoped override to patched Satori 0.33.5 built and
passed unit tests, but the actual Worker returned 500: HarfBuzz reads the
absent `self.location.href`. Upstream confirms a second WASM-compilation
restriction; a browser-global shim is not a valid fix. The override was removed.

Replace the old renderer with **takumi-js 2.19.0**, licensed MIT OR Apache-2.0.
Its maintained `ImageResponse` API selects a precompiled WASM backend on
Workers. The Astro API uses a typed React card component and awaits `ready`
before caching or returning. It retains dynamic query-driven cards, clipping,
PNG output, the one-day edge cache, debug errors, and the existing static
fallback. Satori and its newly introduced vulnerable fflate path are absent.
There is no custom HTML parser, generated page snapshot, or WASM-loader shim.

Takumi fetches images referenced by CSS, so the endpoint uses the framework's
`isEmojiImageUrl` helper as `images.allowUrl`. This retains default Twemoji
rendering but rejects arbitrary image URLs before fetching, including redirects.
The Worker regression detected one loopback image request before the policy
and zero after it. An invalid query-driven background follows the existing
debug-500/fallback contract. A real emoji card and named CSS colour also rendered.

The installed renderer, helpers, WASM and native-core packages all declare
MIT OR Apache-2.0 and have no install lifecycle scripts. Registry metadata
lists one maintainer and npm provenance attestations. Exact versions and
lockfile integrity pin the artifacts; this review did not verify the attestations
or reproduce their Rust/native/WASM builds. The single-maintainer and binary
dependency risks remain maintenance considerations.

- [Satori advisory](https://github.com/advisories/GHSA-wx4j-mvgx-mqwp)
- [Confirmed Workers incompatibility](https://github.com/vercel/satori/issues/878)
- [Takumi runtime support](https://takumi.kane.tw/docs)
- [ImageResponse lifecycle and errors](https://takumi.kane.tw/docs/reference/image-response)
- [Takumi 2.19.0 package metadata](https://registry.npmjs.org/takumi-js/2.19.0)
- [Renderer image URL policy](https://takumi.kane.tw/docs/images#urls-from-user-input)

### Diagram compatibility exception

`mermaid-isomorphic@3.1.0` still declares Mermaid ^11 and KaTeX ^0.16.0.
The scoped overrides deliberately exceed those ranges: **Mermaid 12.3.0**
and **KaTeX 0.18.2**. This is locally qualified compatibility, not upstream
range support. Mermaid 12 itself declares KaTeX ^0.18.0. Its published browser
bundle embeds KaTeX **0.18.11**, verified in the installed artifact; updating
only the standalone KaTeX dependency would leave the old Mermaid bundle in use.
That bundled patch is upstream-deprecated for accidental breaking changes,
not the old trust-bypass advisory. It was not separately pinned or vendored.

Keep neutral/classic/Dagre options to avoid Mermaid 12's changed layout/look
defaults. A real Astro Markdown processor test verifies accessible diagram
labels and mathematical labels (`x²`); actual Markdown and MDX routes retain
normalized inline SVGs and the site's theme/zoom enhancement. Remove these
overrides once the parent declares compatible patched ranges, then requalify
the build-time browser renderer. No malicious diagram was executed.

- [Mermaid 12 release changes](https://github.com/mermaid-js/mermaid/releases/tag/mermaid%4012.0.0)
- [Mermaid package metadata](https://registry.npmjs.org/mermaid/12.3.0)
